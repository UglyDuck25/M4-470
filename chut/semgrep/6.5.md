# Experiment 6.5: Comparison with Semgrep

## Semgrep Setup
- **Tool**: Semgrep 1.156.0, installed via `pip3 install semgrep` in the M4 Docker container (Debian 12)
- **Config**: `--config 'r/java'` — Java rules from the Semgrep Registry (312 rules downloaded, 114 applicable to scanned files)
- **Target**: `gson/src/main/java` (86 Java source files, tests excluded per instructions)

> **Note on `r/` vs `p/`**: `r/java` pulls all community-contributed registry rules for Java (broader coverage). `p/java` is a smaller curated pack (60 rules). We used `r/java` for wider coverage; because `p/java` produced 0 findings on Gson.

## Command Executed
```bash
semgrep --config 'r/java' --json /m4/gson/gson/src/main/java > semgrep-java-ruleset.json 2> semgrep-java-stderr.log
```

## Collected Metrics

**Semgrep**: 1 finding, 114 rules on 86 files, ~5.3s runtime.

- **Rule**: `java.lang.correctness.hardcoded-conditional.hardcoded-conditional`
- **File**: `Excluder.java`, line 203
- **Severity**: ERROR
- **Message**: "This if statement will always have the same behavior and is therefore unnecessary."

**Infer** (baseline from Experiment 6.2): 14 findings (all Thread Safety Violation), ~1m 20s runtime, across 4 files.

## Discussion

### 1. Did both tools report issues in the same files or methods?

**No.** Zero overlap. Infer flagged 4 files (`JsonStreamParser.java`, `DefaultDateTypeAdapter.java`, `SqlDateTypeAdapter.java`, `SqlTimeTypeAdapter.java`) for concurrency issues. Semgrep flagged a different file entirely (`Excluder.java`) for a hardcoded conditional. The tools analyzed completely different dimensions of code quality.

### 2. Why might Semgrep detect issues that Infer does not?

Semgrep is a static analysis tool that searches code for user-defined or community-defined rule-based patterns. Thus, it finds bugs, enforces code standards, and detects security vulnerabilities using pattern-matching rules — without requiring execution path reasoning. Infer focuses exclusively on behavioral failures (null dereferences, resource leaks, data races), so a hardcoded conditional falls outside its scope.

### 3. Why might Infer detect issues that Semgrep does not?

Infer performs **path-sensitive, interprocedural analysis**. The thread safety violations it found in Gson involve indirect writes across multiple call layers (e.g., `Streams.parse(parser)` → `fillBuffer()` → write to `parser.limit`), require modeling synchronization primitives and their absence, and depend on constructing feasible execution traces. Semgrep cannot detect these because it lacks interprocedural data-flow tracking, has no concurrency model, and operates on syntactic patterns rather than execution semantics.

### 4. Which tool appears more useful for detecting runtime failures?

**Infer** is more useful for runtime failure detection in Gson. All 14 of its findings identify potential concurrency failures — actual behavioral risks if classes were used in multi-threaded contexts. Semgrep's single finding is a code quality issue (always-true conditional) that will not cause a crash or incorrect output at runtime. For a serialization library like Gson where type adapters and stream parsers could conceivably be shared across threads, Infer's path-sensitive reasoning provides more actionable safety warnings. Semgrep complements this as a fast, broad scanner for patterns and security issues, but is not designed to reason about runtime failure paths.
